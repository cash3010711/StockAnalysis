# Design

## Context

- 工作區只有 `openspec/` 與 `.agents/`，沒有任何既有程式碼，所以從零建立。動機見 proposal.md 的「Why」，行為需求見 `specs/`。
- 只在 Windows 本機執行，單一使用者，沒有登入，也不對外部署。
- 資料源為 FinMind 免費方案（需要 token、每小時約 600 次請求），因此快取策略是設計重點。
- 勝率必須來自回測，而且回測不能偷看未來資料，這是本設計最核心的正確性約束。

## Goals / Non-Goals

**Goals:**
- 分析核心（指標、三層條件、回測）是純函式、可決定性、可單元測試，不依賴網路或資料庫。
- 「今日分析」與「歷史回測」共用同一套條件程式碼，保證兩者規則一致。
- 首次分析一檔股票在 FinMind 額度內完成；再次分析主要讀快取，數秒內回應。

**Non-Goals:**
- 不做背景排程或預先抓取全市場資料。
- 不做策略或參數的可插拔設定介面（參數集中寫成常數，方便日後再開放）。
- 不追求向量化回測的極致效能；單檔 5 年約 1,200 根 K 棒，逐日迴圈就足夠。

## Decisions

### 1. 專案結構：monorepo，前後端分開
```
backend/   Python 3.12, FastAPI, pandas, numpy, SQLite（套件管理用 uv）
  app/
    api/          HTTP 路由（只做請求解析與回應組裝）
    data/         FinMind 用戶端、SQLite 快取、公布日推算
    analysis/     indicators.py、layers.py（三層條件）、strategies.py、exits.py
    backtest/     engine.py、stats.py
  tests/          pytest；analysis／backtest 用固定的 CSV fixture
frontend/  React + TypeScript + Vite + TradingView Lightweight Charts
```
- **為什麼：** 前後端職責清楚。分析核心放在 `analysis/` 與 `backtest/`，不 import `data/` 或 `api/`，可以獨立測試。
- **替代方案：** Streamlit 單一應用。開發較快，但 K 線標記與互動受限，已在訪談中排除。

### 2. 「時點正確」的資料視圖（核心）
- 所有資料表都帶 `effective_date` 欄位：
  - 日 K、法人、融資：當天收盤即生效。
  - 月營收：使用資料源的公布日；沒有時用次月 10 日。
  - 季財報：使用公布日；沒有時用法定期限（Q1 5/15、Q2 8/14、Q3 11/14、Q4 隔年 3/31）。
- 分析核心只透過 `as_of(date)` 取得資料，它只回傳 `effective_date <= date` 的資料。今日分析就是 `as_of(最近收盤日)`，回測則對每個歷史日期呼叫同一套條件。
- **為什麼：** 從結構上杜絕未來函數偏差，而不是靠每個策略自己小心處理。
- **替代方案：** 依資料所屬期間對齊。較簡單，但會讓勝率虛高，已在訪談中排除。

### 3. 預先計算序列，避免逐日重算
- 回測前一次算好所有指標序列（MA、ATR、MACD、KD、20 日高點、量能），以及每日的三層判定布林序列，再由回測引擎逐日走訪。基本面判定以 `effective_date` 做 as-of join（`pandas.merge_asof`）展開成每日序列。
- **為什麼：** 兼顧正確性（仍是時點正確）與效能，邏輯也容易測試。

### 4. 回測引擎規則
- 逐日狀態機：`空手 → 訊號日 → 隔日開盤進場 → 持倉（檢查跳空、停損、停利、到期）→ 空手`。
- 細節規則：
  - 同一根 K 棒同時觸及停利與停損時，判為停損。
  - 開盤跳空越過停損時，以開盤價出場。
  - 停利、停損價在進場時以訊號日的 ATR 固定，之後不移動。
  - 價格依台股升降單位四捨五入。
- 每個策略產生兩次回測：三層條件與純技術面，共用同一個引擎，只差在進場條件遮罩。

### 5. 資料取得與快取
- SQLite 單檔：`backend/data/cache.db`。每個資料集一張表，主鍵是 `(stock_id, date)`。另有 `fetch_log` 表記錄每個（股票, 資料集）最後抓取日期。
- 增量抓取：從 `fetch_log` 最後日期的隔天抓到今天；如果今天還沒收盤（台北時間 14:30 前），只抓到前一個交易日。
- 額度用盡（HTTP 402 或回應訊息）就停止抓取，回傳「部分資料＋警示」或錯誤（見 `market-data` spec）。
- token 放在 `backend/.env` 的 `FINMIND_TOKEN`，並提供 `.env.example`。`.env` 與 `cache.db` 加入 `.gitignore`。

### 6. API 介面
- `GET /api/stocks?q=` 回傳最多 10 筆候選。
- `GET /api/analysis/{stock_id}` 一次回傳完整結果：評估日、資料警示、三層摘要、每個策略的今日狀態與點位、兩組回測統計、交易明細、繪圖用的 OHLCV。
- 錯誤統一格式為 `{code, message, hint}`，例如 `TOKEN_MISSING`、`QUOTA_EXCEEDED`、`STOCK_NOT_SUPPORTED`。
- **為什麼用單一端點：** 個人使用、一次看完整頁，避免前端協調多個請求；回應大小約數百 KB，可以接受。

### 7. 前端
- 單頁三區塊：查詢框（debounce 250ms 自動完成）、三層摘要卡片＋策略比較表、K 線圖。
- 圖表用 Lightweight Charts 的 candlestick 加 histogram，以 series markers 標示交易，以 price lines 標示今日點位。
- 開發時用 Vite proxy 將 `/api` 轉到 `localhost:8000`。

### 8. 預設門檻集中管理
- 規格中的門檻值集中在 `analysis/params.py`：營收年增 > 0、近四季 EPS > 0、負債比 < 60%、法人 10 日買超、融資 10 日增幅 < 20%、ATR 2／3 倍、持有 20 日、樣本門檻 20 筆。
- 這些是合理的起始預設值，不是最佳化的結果。日後要調整時只改這個檔案，並同步修改規格。

## Risks / Trade-offs

- [FinMind 資料集名稱或免費額度變動] → 所有 FinMind 呼叫集中在 `data/finmind_client.py`，並有錄製回應的整合測試；資料集名稱在實作第一步驗證。
- [資料源沒有提供實際公布日] → 使用法定期限作為保守的生效日：寧可晚生效，也不偷看未來。
- [首次分析要打約 5 個資料集，可能較慢] → 前端顯示載入狀態；之後主要讀快取。
- [固定門檻對某些產業不適用（例如金融股的負債比天生偏高）] → MVP 接受這個限制，並在結果中顯示實際數值，讓使用者自行判斷；產業別門檻列為日後改進。
- [回測勝率本身仍有過度擬合與倖存者偏差] → 不最佳化參數、顯示樣本不足警示與純技術面對照，並固定顯示免責說明。
- [還原權值價格與實際成交價不同] → 回測與指標都使用還原價，以保持一致；顯示今日點位時也用還原價，評估日當天的還原價等於實際價，所以不影響今日點位。

## Open Questions

- FinMind 季財報資料集是否附實際公布日？這會影響生效日的精確度，但不影響架構：沒有的話就用法定期限，實作時確認即可。
